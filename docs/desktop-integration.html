桌面端接口对接

Electron 桌面端（apps/desktop，55.5 万行 TypeScript）到底调了 Hermes 后端的哪些接口、这些调用散落在哪些模块和文件里，以及它是怎么连上后端的。 调用点由正则 + 逐文件阅读源码双重核实，后端接口全集取自运行时真值。

194 / 281HTTP 接口覆盖

后端 281 条 HTTP 路由里，桌面端用到 194 条。未用的 87 条集中在 Web 版仪表盘专属功能上。

123 / 225JSON-RPC 覆盖

后端 225 个 JSON-RPC 方法里，桌面端调了 123 个。对话、会话、工具全靠这一层。

193IPC 通道

渲染进程碰不到 HTTP，所有 REST 都得让主进程代发——这就是通道数量如此之多的原因。

调用面概览

桌面端跟后端打交道有三条通路，走哪条不是随意的，取决于是谁发起、要不要长连接。

① 渲染进程 → IPC → 主进程 → HTTP

ipcRenderer.invoke('hermes:api')

所有 REST 调用的唯一路径。渲染进程本身不发 HTTP，凭据只存在主进程里。193 个 IPC 通道基本都是为这条链路服务的。

② 渲染进程 → WebSocket 直连

/api/ws　JsonRpcGatewayClient

反过来：渲染进程只向主进程要一个带一次性票据的 URL，然后自己直连后端。对话、事件流都在这条上。

③ 主进程直接调

electron/*.ts

后端存活探测、端口发现、更新交接、SSH 隧道这类不涉及界面的，主进程自己发。

和 Web 版仪表盘的关键差异

两者共用同一个后端，但终端实现完全不同：Web 版用 xterm.js 接后端的 /api/pty（后端 spawn 一个真实 hermes --tui）；桌面端用 Electron 内置的 node-pty 在本地起 shell，经 IPC 通信，根本不碰 /api/pty。/api/events、/api/pub 同样只有 Web 版在用。

1. 后端进程从哪来

1.1 spawnOwnedBackend 本身

apps/desktop/electron/main.ts:1428-1438 中 spawnOwnedBackend 只是对 Node child_process.spawn 的一层包装，接管到 localBackendLifecycle（生命周期计数/取消）里：

function spawnOwnedBackend(...args) {
  const child = localBackendLifecycle.spawn(() => spawn(...args))
  child.once('exit', () => localBackendLifecycle.release(child))
  ...
}

真正“派生什么命令”由调用方（resolveHermesBackend 解析出的 backend.command/backend.args）决定，见 1.2。

1.2 两处调用点：主 backend vs 池 backend

  • 池 backend（非主 profile，按需惰性启动）：main.ts:12580-12610。命令行为

['--profile', profile, 'serve', '--host', '127.0.0.1', '--port', '0']（main.ts:12557）。

  • 主 backend（桌面启动 profile，唯一常驻）：main.ts:13028-13063。命令行为

['serve', '--host', '127.0.0.1', '--port', '0']，若设置了 activeProfile 则前置

--profile <name>（main.ts:12962-12972）。

两者区别（main.ts:1452-1467 注释说明）：

  • 主 backend 由 backendConnectionState + startHermes() 管理，永远存在（桌面启动 profile）。
  • 池 backend 存于 backendPool = Map<profile, {process, port, token, ...}>（main.ts:1458），是额外profile 的按需 backend，仅在切到非主 profile 会话时惰性拉起，受 pool-limits.ts / pool-eviction.ts 的容量与空闲回收管理（LRU + idle reap，main.ts:1460-1467）。单 profile 用户永远不会填充这个 Map。
  • 两处 spawn 参数结构几乎一致：都注入 HERMES_HOME、TERMINAL_CWD、HERMES_DASHBOARD_SESSION_TOKEN、HERMES_DESKTOP=1、父进程看门狗环境变量、HERMES_WEB_DIST（main.ts:12585-12609、main.ts:13033-13059）。

resolveHermesBackend(backendArgs)（main.ts:5045）决定命令怎么拼，按优先级：

  1. HERMES_DESKTOP_HERMES_ROOT 开发者覆盖源码目录（main.ts:5049-5057）；
  2. 非打包时的本地源码 checkout SOURCE_REPO_ROOT（main.ts:5060-5068）；
  3. 已完成首启安装的 ACTIVE_HERMES_ROOT（venv + 仓库）——createActiveBackend（main.ts:5071-5088）；
  4. PATH 上已存在的 hermes（用户自装，不写 bootstrap marker，main.ts:5096-5120 起）；
  5. 都没有则走首启安装引导（bootstrap）。

命令形态最终是 python -m hermes_cli.main <backendArgs>（见 createPythonBackend，main.ts:4989）或 PATH 上的 hermes 可执行文件。

若解析出的运行时不支持 serve 子命令（旧版本），getBackendArgsForRuntime（main.ts:2653）会把参数改写为兼容的 dashboard --no-open（backend-command.ts:30 的 dashboardFallbackArgs）。

1.3 端口怎么拿到

--port 0：交给 OS 分配临时端口，子进程自行绑定后向 stdout 打印哨兵行。两条路径都存在，由 waitForDashboardPortAnnouncement（apps/desktop/electron/backend-ready.ts:221-246）二选一：

  • stdout 哨兵（默认/当前实际生效路径）：正则 /^HERMES_(?:BACKEND|DASHBOARD)_READY port=(\d+)/m（backend-ready.ts:10），由 waitForDashboardPort 监听 child.stdout 的 data 事件按行匹配（backend-ready.ts:64-141）。为兼容 uvicorn stderr 无换行导致哨兵被拼接的情况，还准备了合并缓冲区正则 READY_IN_MERGED_OUTPUT_RE（backend-ready.ts:14）。超时默认 90s，可用 HERMES_DESKTOP_PORT_ANNOUNCE_TIMEOUT_MS 覆盖，下限 45s（backend-ready.ts:19-38）。
  • ready 文件：waitForDashboardReadyFile 轮询（50ms 间隔）读取 JSON 文件里的 port 字段（backend-ready.ts:145-219）。触发条件是调用方传入了 options.readyFile（backend-ready.ts:242-244），而 readyFile 来自 backend.readyFile ? makeDashboardReadyFile() : null（main.ts:12563、main.ts:13014）。
  • 注意：在当前代码里，本次检索未找到任何路径把 backend.readyFile 置为真值（resolveHermesBackend/createPythonBackend/createActiveBackend 均未设置该字段）。也就是说 ready-file 分支目前是已实现但未被任何解析路径触发的保留开关（可能是给未来某个运行时/平台预留的兼容开关），线上默认恒定走 stdout 哨兵路径。写文档时建议明确标注这一点，不要写成"两者按条件切换"而误导为都在用。

1.4 其它连接模式

resolveRemoteBackend(profile, options)（main.ts:10831）统一解析出 3 种远程路由（由 resolveDesktopRemoteRoute 给出 route.kind）：

  • ssh：走 bootstrapSshConnection(...)（main.ts:10521→10606），内部：
  • SshConnection（apps/desktop/electron/ssh-connection.ts）用系统 ssh 客户端管理 ControlMaster（ssh -O ...，ssh-connection.ts:266）；
  • forward(localPort, remotePort)（ssh-connection.ts:953）在支持 ControlMaster 的平台走 -O forward（复用 master 通道，ssh-connection.ts:988），在不支持 mux 的 Windows OpenSSH 上才真正 spawn 一个持久的 ssh -N -L <local>:<remote> -- 子进程作为隧道本身（ssh-connection.ts:948-967，-N/-L 参数见 962-964）；
  • 远端进程通过 SSH exec 拉起（remote-lifecycle.ts 的 buildSpawnCommand，remote-lifecycle.ts:1041-1080）：setsid/nohup 分离运行 hermes serve --isolated --host 127.0.0.1 --port 0 [--ssh-session-token-file ... --ssh-owner-nonce ...]（remote-lifecycle.ts:1046-1048），随后 ssh.forward(localPort, remotePort) 建立本地→远端端口转发，再用 waitForHermes(baseUrl, token, ...) HTTP 探活（main.ts:10665、main.ts:6601）。
  • url/cloud（远端已在跑的 backend，桌面只是连过去）：buildRemoteConnection(rawUrl, authMode, token, ...)（main.ts:10040），authMode 为 'token' 或 'oauth'。
  • 主 profile 走托管更新恢复快照：managedPrimaryRestoreOwners（main.ts:10836-10877）单独处理更新事务中断后的精确重连，同样落到 bootstrapSshConnection。

resolveDesktopRemoteRoute 解出的字段（结合 main.ts:10877-10887）包括：kind（'ssh'|'url'|'cloud'|本地）、ssh 配置、token/authMode、url、headers、connectionId、source（'profile'|'registry:<id>'|'env'）。

2. 鉴权

2.1 session token 的来源

桌面端生成、注入给后端，而不是后端生成后回报。 两处 spawn 都是：

const token = crypto.randomBytes(32).toString('base64url')   // main.ts:12523 (池) / main.ts:12960 (主)
...
env: { ..., HERMES_DASHBOARD_SESSION_TOKEN: token, ... }       // main.ts:12594 / main.ts:13047

但后端才是"实际在服务的 token"的最终事实来源——apps/desktop/electron/dashboard-token.ts:1-8 注释明确写道：主进程可以在 spawn 时传 HERMES_DASHBOARD_SESSION_TOKEN，但 dashboard 对它实际提供服务的 token 才是真相；如果两者漂移（例如复用了一个已经在跑、token 不同的旧进程），HTTP 探活会通过但 /api/ws 会拒绝渲染进程的 token。为此，spawn 完成后统一调用 adoptServedDashboardToken(baseUrl, token, {...})（本地：main.ts:12688、main.ts:13187；远程 SSH：remote-lifecycle.ts 里作为 adoptServedToken 依赖注入，main.ts:10667）——它会 fetch dashboard 首页 HTML，从 window.__HERMES_SESSION_TOKEN__ = "..." 里把服务端真正在用的 token 抠出来（dashboard-token.ts:37-49、dashboard-token.ts:88）作为最终采用值。

远程 url/cloud/oauth 模式的 token/ticket 不是桌面生成的，而是用户在 Settings→Gateway 里保存的静态 token（connection-config.ts 持久化，解密见 decryptDesktopSecret）或 OAuth 会话（见 2.4）。

2.2 HTTP 请求怎么带凭据

统一走 apps/desktop/electron/main.ts:5418 的 fetchJson(url, token, options)，用 Node 原生 http/https（走 api-transport.ts 的 keep-alive Agent 池，api-transport.ts:38-48）手写请求，请求头：

'X-Hermes-Session-Token': token,                              // main.ts:5452 —— 本地/SSH 隧道场景
...(options.bearer ? { Authorization: `Bearer ${options.bearer}` } : {})  // main.ts:5458 —— OAuth 原生流程

即：本地/SSH-token 模式走自定义头 X-Hermes-Session-Token；OAuth（RFC 8252 native flow）走标准 Authorization: Bearer（main.ts:5453-5458）。fetchJson 内置幂等重试策略（api-transport.ts 顶部大段注释：GET/HEAD/OPTIONS 任意瞬时错误重试；POST/PUT/PATCH/DELETE 只在"确定没打到服务端"时重试，避免重复提交）。

例外：dashboard-token.ts:20 的 fetchPublicText 用的是浏览器风格全局 fetch()（Node 18+ 内置），仅用于"发现已在跑 backend 真正下发的 token"这一只读场景，不是通用请求路径。

2.3 WebSocket 怎么带凭据

/api/ws 的 URL 由 apps/desktop/electron/connection-config.ts 两个函数拼出：

  • token 模式：.../api/ws?token=<token>（connection-config.ts:104-110）；
  • OAuth 模式：.../api/ws?ticket=<ticket>（connection-config.ts:112-118），ticket 由 mintGatewayWsTicket(baseUrl, headers)（main.ts:8294，实现在 oauth-rest-request.ts:53-90）向 POST {baseUrl}/api/auth/ws-ticket 现铸一次性票据，单次使用、不可重放地绑定到当前 OAuth 会话（原生 bearer 优先，失败回退 cookie，oauth-rest-request.ts:33-42）。
  • ?internal=：本次检索在 apps/desktop/electron/*.ts 与 apps/shared/src/* 中均未找到该查询参数的桌面端实现（grep -rn "internal=" apps/desktop apps/shared 无命中）。判断：这不是桌面端使用的鉴权模式，题面描述的三种模式里桌面端只实际使用 ?token= 和 ?ticket= 两种；?internal= 若存在，应在后端 hermes_cli/web_server*.py 内部（例如允许后端自身/回环调用跳过校验），未找到，不编造，建议向后端团队复核。

JsonRpcGatewayClient.connect(wsUrl)（apps/shared/src/json-rpc-gateway.ts:169）本身只接受完整 ws:///wss:// URL 字符串（isGatewayWebSocketUrl，json-rpc-gateway.ts:104），鉴权参数已经在 URL 里，Client 不单独处理 header。

2.4 SSH 隔离模式的桌面端配合

远程 SSH 场景下，Desktop 不把明文 token 作为 CLI 参数传给远端进程（避免 ps 泄露），而是：

  1. 生成 spawnNonce = crypto.randomBytes(8).toString('hex') 与 tokenFilePath = spawnTokenPath(ownershipId, spawnNonce)（remote-lifecycle.ts:1194-1196）；
  2. 通过 SSH exec 执行一段内联 Python，把 token 从 stdin 写入远端一个 0700 目录下 0600 权限、O_EXCL|O_NOFOLLOW 原子创建的文件，并做目录属主/权限校验、清理 1 小时以上的陈旧 token 文件（remote-lifecycle.ts:1198-1229，stdinData: token 见 1229）；
  3. 用 --ssh-session-token-file <tokenFilePath> --ssh-owner-nonce <spawnNonce> 启动远端 hermes serve --isolated（remote-lifecycle.ts:1046-1048，拼接逻辑见 buildSpawnCommand）；
  4. 后续对该远端进程的终止操作会校验命令行中确实包含相同的 --ssh-owner-nonce/--ssh-session-token-file（防止 PID 复用后误杀别的进程），例如 remote-lifecycle.ts:617-623（Python 侧参数位置校验）与 remote-lifecycle.ts:758-759（shell case 校验 --ssh-owner-nonce $nonce / --ssh-session-token-file $token 是否出现在 cmdline 里）。
  5. 若远端 Hermes 版本太旧、不支持这两个 flag，会探测 serve --help 是否包含 ssh-session-token-file/ssh-owner-nonce（remote-lifecycle.ts:1128-1129），不支持则报错要求升级（remote-lifecycle.ts:1186）。

3. 通信通道

3.1 /api/ws（JSON-RPC）——JsonRpcGatewayClient

实现：apps/shared/src/json-rpc-gateway.ts；桌面端子类：apps/desktop/src/api/client.ts:27-36 的 HermesGateway extends JsonRpcGatewayClient。

  • 连接建立：connect(wsUrl)（json-rpc-gateway.ts:169）校验 URL 后 new WebSocket(wsUrl)（或注入的 socketFactory），state 走 idle → connecting → open/error/closed（json-rpc-gateway.ts:38）。open 事件触发后立即 void this.fetchReplay()（json-rpc-gateway.ts:241，见下）。连接有超时保护（默认 15s，DEFAULT_CONNECT_TIMEOUT_MS，json-rpc-gateway.ts:101），超时则关闭半开 socket 并置 error 状态（json-rpc-gateway.ts:258-281）。
  • 请求-响应配对：request(method, params, timeoutMs, signal)（json-rpc-gateway.ts:345）用自增 nextId（可自定义前缀/生成器）生成 id，登记到 pending: Map<id, {resolve, reject, timer}>（json-rpc-gateway.ts:118、414），发送 {jsonrpc:'2.0', id, method, params}；收到帧后按 frame.id 在 handleMessage（json-rpc-gateway.ts:433-464）里查表 resolve/reject（区分 frame.error / frame.result），并支持超时（默认 120s，DEFAULT_REQUEST_TIMEOUT_MS）与 AbortSignal 取消（json-rpc-gateway.ts:383-412）。桌面端对 prompt.submit 等长任务单独放宽到 30 分钟（apps/desktop/src/api/client.ts:24-26 的 PROMPT_SUBMIT_REQUEST_TIMEOUT_MS），因为回合完成靠事件流通知而非该 RPC 的返回。
  • 事件帧分发：无 id 且 method === 'event' 的帧（json-rpc-gateway.ts:466）按 frame.params.type（GatewayEventName）分发给通过 on(type, handler) / onAny(handler) 注册的处理器（json-rpc-gateway.ts:317-336、724-732），同时维护每 session 的 lastSeenSeq 水位（recordSeq，json-rpc-gateway.ts:503-516）用于重连重放。gateway.ready 事件里若 payload.heartbeat === true 则启动心跳（json-rpc-gateway.ts:467-474，心跳实现见 startHeartbeat，json-rpc-gateway.ts:655-687：每 15s 发 gateway.ping，45s 未收到任何入站消息则判定心跳超时并使当前 socket 失效）。
  • 断线重连：由 JsonRpcGatewayClient 自身不做自动重连（无内部定时器发起 connect），只负责单次连接的心跳/超时/失效上报（invalidateSocket，json-rpc-gateway.ts:696-712）；重连策略/退避在上层（Desktop 的 store/主进程重连协调，如 backendDialClaims、primary-connection-rehome.ts 等）实现，不在本文件职责内。
  • 事件重放 fetchReplay（约 530 行）：json-rpc-gateway.ts:530-595。触发时机：每次 connect() 的 onOpen 之后自动调用一次（json-rpc-gateway.ts:241）。逻辑：
  1. 若无任何已知 lastSeenSeq 水位或已有重放在途，直接跳过（530-533）；
  2. 为每个已知 session_id 建立 replayHold（暂存重放期间到达的实时帧，避免与重放结果乱序/重复，535-545）；
  3. 对每个 session 并发调用 RPC session.events.since，携带 {session_id, last_seen}，超时 10s（REPLAY_REQUEST_TIMEOUT_MS，json-rpc-gateway.ts:95、551-558）；
  4. 用响应里的 epoch 与本地 replayEpoch 比对：不一致说明后端重启过、旧的 seq 水位失效，调用 adoptReplayEpoch 清空水位重新计数（566-579、623-633）；
  5. 把返回的历史事件通过 dispatchIfNewer（仅在 seq 严格大于水位时才派发，601-616）送出，最后 flushReplayHold 把重放期间暂存的实时帧也按同样的去重规则放出（592、636-649）。
  6. 整个过程 best-effort、吞掉异常（589-591），是"有损重连"之上的一层优化，不保证。
  • GatewayEventName 枚举（json-rpc-gateway.ts:1-25）：gateway.ready、session.info、session.usage、message.start、message.delta、message.interim、message.complete、thinking.delta、reasoning.delta、reasoning.available、status.update、tool.start、tool.progress、tool.complete、tool.generating、todo.updated、clarify.request、approval.request、sudo.request、secret.request、background.complete、error、skin.changed，外加 (string & {}) 兜底（未来新事件类型不必更新此联合类型也能通过类型检查）。

3.2 其它 WS 通道（/api/pty、/api/events、/api/pub）

  • 全仓库检索（grep -rn "api/pty|api/events|api/pub" apps/desktop）均无命中——桌面端代码里没有直接连接这三个端点。
  • /api/pty：桌面端的内嵌终端功能并不经由后端的这个 WS 端点，而是在 Electron 主进程本地用 node-pty 直接起一个真实 shell 进程（apps/desktop/electron/terminal-ipc.ts:1-3 注释、terminal-ipc.ts:10 import nodePty from 'node-pty'），通过 hermes:terminal:* 系列 IPC 通道把输出流转给 renderer；SSH 场景则用 buildInteractiveSshArgs（ssh-connection.ts）拼交互式 ssh 命令。也就是说：桌面端“终端”是本地 PTY + IPC，不是 WS 通道。
  • /api/events、/api/pub：仅在 web/src（独立 Web 版仪表盘，非 Electron 应用）中使用，例如 web/src/components/ChatSidebar.tsx:15,242-243,339、web/src/lib/events-reconnect.ts:2，用于浏览器多标签页之间的旁路事件订阅/广播。apps/desktop/src 有自己独立实现的 app/chat/sidebar/index.tsx，并未复用 web/src 的这套订阅逻辑，全部落在 /api/ws 单一 JSON-RPC 通道上。结论：桌面端不使用 /api/pty、/api/events、/api/pub 这三个 WS 端点，它们是给独立 Web 前端和/或非桌面客户端用的。

3.3 普通 HTTP（fetch）与统一封装

  • 渲染进程侧没有统一的 fetch 封装，也基本不直接 fetch 后端。渲染进程通过 apps/desktop/src/api/client.ts:96-105 的 hermesApi<T>(request) 调用 window.hermesDesktop.api<T>({...connectionScoped(), ...request})，也就是走 preload 暴露的 IPC 桥（preload.ts:258：api: request => ipcRenderer.invoke('hermes:api', request)），把请求"甩给"主进程处理。
  • 真正发起 HTTP 请求的是主进程：ipcMain.handle('hermes:api', ...)（main.ts:16727）→ handleHermesApiRequest(request)（main.ts:16649）→ ensureBackend(routeProfile, ...) 解析连接 → fetchJsonForBackend(connection, path, {...})（main.ts:15994，最终落到 2.2 节的 fetchJson，用 Node http/https 手写请求 + 连接池，见 api-transport.ts）。
  • base URL 拼接：本地/池 backend 恒为 http://127.0.0.1:<port>（main.ts:12684、main.ts:13181，port 来自 1.3 节的端口发现结果）；远程走 normalizeRemoteBaseUrl(rawUrl)（main.ts:10050，在 buildRemoteConnection 内，规整协议/去尾斜杠/清空 query&hash）。
  • apps/shared/src/websocket-url.ts 的 buildHermesWebSocketUrl(options)（websocket-url.ts:135-151）是渲染端通用的 ws URL 构造工具：按 window.location.protocol/host 推导 ws:/wss:，拼 basePath + path + ?query（含 authParam），供非 Electron 场景（如独立 Web 前端、或渲染进程内部某些直连场景）使用；桌面端主进程侧的等价物是 connection-config.ts 的 buildGatewayWsUrl/buildGatewayWsUrlWithTicket（3.1 节已引用）。resolveGatewayWsUrl(deps, conn)（websocket-url.ts:39-94）是共享的“连接前重新铸造一次 URL”封装：OAuth 模式必须每次现铸一次性 ticket（否则重放会被拒绝，websocket-url.ts:43-79），非 OAuth 模式尽量取新 URL、拿不到则回退旧的 conn.wsUrl（websocket-url.ts:81-93）。

4.1 preload 暴露的 API

apps/desktop/electron/preload.ts:15 通过 contextBridge.exposeInMainWorld('hermesDesktop', {...}) 暴露一个大对象，节选关键项（preload.ts:15-60起）：

  • api(request) → ipcRenderer.invoke('hermes:api', request)（HTTP 请求统一入口，preload.ts:258）；
  • getConnection(profile, opts) / getConnectionFor(payload)（preload.ts:26-27）：解析出连接描述符（baseUrl/token/wsUrl 等）；
  • getGatewayWsUrl(profile) / getGatewayWsUrlFor(payload)（preload.ts:31-33）：现铸一次新的 /api/ws URL（对应 3.1 节 resolveGatewayWsUrl 的 getGatewayWsUrl 依赖）；
  • getPoolLimits/setPoolLimits、touchBackend、revalidateConnection（preload.ts:28-30）：池管理；

4.2 renderer 直连 vs 经 main 转发

两种都有，按通道类型区分：

  • HTTP（REST 语义的 /api/...）：必须经 main 转发。渲染进程从不直接 fetch() 后端——hermesApi()（apps/desktop/src/api/client.ts:96）统一走 ipcRenderer.invoke('hermes:api', ...)，理由包括：token 由主进程持有/刷新、多 profile/多远程连接路由需要主进程的注册表和 backend 池状态（handleHermesApiRequest 里大量 profile/registry 路由逻辑，main.ts:16649-16725）、以及删除/重命名 profile 期间需要与 backend 生命周期互斥（profileDeletionGate，main.ts:16752）。
  • WebSocket /api/ws（JSON-RPC 网关）：渲染进程直接连接，不经 main 转发数据帧。渲染进程先通过 IPC（getGatewayWsUrl/getConnection）向 main 要一个当前有效的 ws://.../api/ws?token=... 或 ?ticket=... URL，再在渲染进程里 new HermesGateway().connect(wsUrl)（apps/desktop/src/api/client.ts:27），后续所有 JSON-RPC 请求/事件流都是渲染进程 ↔ 后端的直连 WebSocket，main 不参与转发（只负责铸造/刷新 URL、管理 backend 本身的生死）。
  • 二者的分工原则："是否需要凭据新鲜度和多连接路由裁决" 决定要不要经 main——HTTP 请求量大、路由规则复杂（profile/registry/远程），交给 main 统一处理更安全；WS 是长连接，一旦拿到有效 URL，没必要每帧都走 IPC 中转（性能和实现复杂度都不划算），所以直连。
  • 终端 PTY 是第三种模式：既不直连后端 WS，也不是简单的 HTTP 转发，而是纯 IPC 事件流（hermes:terminal:*，主进程本地 node-pty 产生数据后用 ipcRenderer.on/webContents.send 推给渲染进程）。

5. 生命周期

5.1 backend 随 App 退出

app.on('before-quit', event => {...})（main.ts:18228）是主退出钩子：

  • 先处理"托管更新期间不能仓促退出"的特殊情况（main.ts:18242-18259）；
  • 之后 sshBootstrapCoordinator.shutdown()（main.ts:18265）封存 SSH 协调器，防止退出过程中还有重连回调偷偷再拉起 backend；
  • 组装 teardownTasks，其中第一个就是 { run: () => backendShutdown.run(), waitForCompletion: backendNeedsWait }（main.ts:18277），本地/池 backend 的终止最终落到 backend-child.ts 的 waitForBackendExit / 平台相关 kill 逻辑：
  • POSIX：向进程组发信号 process.kill(-pid, 'SIGTERM')（backend-child.ts:9-14 注释 + 实现），因为后端在 POSIX 下以独立会话/进程组运行，直接 child.kill() 只打到直接子进程、打不到它派生的 MCP 孙进程。
  • Windows：forceKillProcessTree(pid) 用 taskkill /T /F 整棵树杀（main.ts:3574-3608），因为 Windows 上没有"负 pid 杀进程组"的等价物，且桌面 spawn 时并未传 Node 的 detached:true（main.ts:3579 注释）。
  • quitTeardown.begin(teardownTasks) 若返回真则 event.preventDefault()，即先跑完清理任务、再真正退出（main.ts:18283-18285）。

"gateway run"（独立的消息平台网关进程）不在这条退出链路里：它由用户/后端自己以 setsid/nohup 方式派生（gateway/run.py 等，属于后端仓库而非桌面代码），与桌面 spawn 的 hermes serve backend 不是同一个进程组/会话，因此 before-quit 的 SIGTERM 并不会波及它——这是有意为之：hermes gateway run 被设计为独立于桌面 App 生命周期的后台常驻进程。桌面端唯一主动接触它生命周期的地方是 Windows 更新交接：apps/desktop/electron/gateway-stop-before-update.ts——在应用内更新前，通过 execFileSync(hermesCliPath, ['gateway', 'stop', '--all'])（gateway-stop-before-update.ts:46-52）主动喊停所有 profile 的消息网关（因为它持有 venv shim 锁，taskkill /T 从 worker 子进程出发够不到其父 launcher），更新中止时再用 ['gateway', 'start', '--all'] 拉回来（gateway-stop-before-update.ts:62-64）。这是 CLI 委托式管理，不是进程树信号。

5.2 父进程死亡看门狗的注入

apps/desktop/electron/parent-process-identity.ts 定义/组装环境变量，main.ts 在两处 spawn 前调用：

const parentStartMarker = await desktopParentStartMarker()
const backendNonce = crypto.randomBytes(16).toString('hex')
const parentIdentityEnv = parentWatchdogEnv(process.pid, parentStartMarker, backendNonce)

（池：main.ts:12575-12577；主：main.ts:13020-13022），随后 ...parentIdentityEnv 展开进子进程 env（main.ts:12601、main.ts:13054）。

  • HERMES_PARENT_PID：恒为桌面 Electron 主进程自身 process.pid（parent-process-identity.ts:75）。
  • HERMES_PARENT_START_MARKER：跨平台的"父进程创建时刻"标记，Windows 上是 winms:<毫秒时间戳>（electronProcessStartMarker，parent-process-identity.ts:21-33，供后端换算成 Windows FILETIME 做同一口径比较），用于让后端区分"同一个真父进程"还是"PID 被复用给了别的进程"；探测失败时降级为仅 PID 看门狗（parent-process-identity.ts:78-80 的 if (startMarker === null) return env）。
  • HERMES_PARENT_NONCE：每次 spawn 随机生成的一次性 backendNonce（16 字节 hex），与 marker 成对出现、要么都有要么都没有（parent-process-identity.ts:82-90 的原子性校验：if (!startMarker || !nonce) throw）。
  • 顺带还会算出 HERMES_SPAWN 标签（v1:-:serve:<pid>:<createSeconds>，parent-process-identity.ts:96-108），供后端 hermes_cli.process_identity 模块做谱系（lineage）校验，serve 是固定 purpose（桌面只会拿它来拉起 backend）。

这套机制让后端可以在桌面异常崩溃（没有走到 before-quit）后自行判断"父进程真的死了"（而不是 PID 被复用），从而自杀退出，避免孤儿 backend 常驻。

  • REST：必须经主进程转发（hermesApi() → window.hermesDesktop.api() → IPC → api-transport.ts → 真实 fetch）。
