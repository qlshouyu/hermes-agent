Hermes-Agent · 架构决策备忘

B 线抽取：采纳的两层方案

把「B · hermes serve 桌面 / Dashboard 后端」剥离出来自建前端， 并在架构上保证永远能跟随上游主线升级。这份文档记录最终采纳的组合、被弃用的选项， 以及让「零冲突」成立的具体 Git 机制。

仓库 qlshouyu/hermes-agent（fork） 上游 NousResearch/hermes-agent 基线 fc71fb63e5 · v0.21.2 日期 2026-09-12

决策

采纳 方案 1 + 方案 3B 的两层组合。 方案 1 提供能力——把 hermes serve 当黑盒后端，前端在仓库外自建； 方案 3B 提供保障——在 hermes-agent 仓库内只新增、不修改任何既有文件， 放一层契约基线与漂移告警。

两者共同的前提是同一件事：对上游文件的修改量必须恒为 0。 这不是靠纪律维持的约定，而是可以用 Git 机制强制保证的不变量——见第三节。

✓ 方案 1 · 黑盒进程 + 外部前端 ✓ 方案 3B · 仓内只加不改 方案 2 · 独立 Python 包 方案 3A · 重构既有文件

一、两层结构

谁拥有什么

三层各自独立演化，中间那层是唯一的接触面。上游层你只读不写，这是整个架构的地基。

方案 1 · 客户端层 你的代码 · 完全自主
自建桌面端与 Web 端，只通过 HTTP + WebSocket 调用后端。 UI、交互、状态管理、技术栈全部自选，不受上游前端任何约束。 独立仓库，与 hermes-agent 无 Git 关系
方案 3B · 守卫层 你的代码 · 仓库内只加不改
契约基线快照（REST + RPC 方法名 + 事件名）与漂移告警。 只新增文件，绝不修改任何既有文件——Git 对新增文件不产生冲突。 hermes-agent 内的专用顶层目录，独立分支
上游层 NousResearch · 只读
hermes serve 的 23,493 行实现、Agent 内核、工具、插件、网关、~/.hermes/ 全部状态。 你 git pull，永远不 commit。 main 分支 = origin/main 的纯镜像

二、为什么这个组合能守住

不是纪律，是数学

Git 冲突的发生条件很明确：两边修改了同一个文件的相邻区域。这个组合刻意让这个条件无法成立。

行为上游是否碰同一文件Git 结果
客户端代码在独立仓库 不可能——不在同一个仓库 无关
在 hermes-agent 内新增文件 除非上游创建同名文件，否则不会 不冲突
在 hermes-agent 内修改既有文件 web_server.py 715 次/年，几乎必然 冲突
向 main 提交任何东西 不涉及文件内容，但 main 与 origin/main 分叉 pull 从快进降级为合并
当前起点是干净的 实测：main 与 origin/main 落后 0 / 领先 0，本仓近 300 次提交的作者全部是上游贡献者。 也就是说这个 fork 目前零自有提交、零冲突债务。下面四条规则的作用就是让这个状态永久保持。

三、保证跟随主线的四条规则

全部已在本仓实测验证
规则 1

main 永远是上游的纯镜像，绝不提交

main 上不放任何自有提交。只要 main 与 origin/main 不分叉， git pull 就永远是快进（fast-forward）——快进合并在定义上不可能冲突。

实测当前状态已满足：git rev-list --left-right --count origin/main...main → 0　0。

规则 2

自有文件放进上游未占用的顶层目录

守卫层的文件放在一个上游从未使用过的顶层目录里，例如 contract/。 已实测确认 contract、contracts、integration、 client、sdk、vendor、local 在 origin/main 中全部未被占用。

反例：docs/ 是上游在积极维护的目录——23 个文件、239 次提交/年。 往那里放自有文件不会立刻出问题，但同名碰撞的概率长期不为零，而且会让「哪些是我的」变得模糊。

规则 3

自有提交放在独立分支，用 rebase 跟随

守卫层的文件需要版本历史，所以要提交——但提交到一条自己的分支上，而不是 main。 同步时先快进 main，再把自有分支 rebase 上去。因为两边文件集不相交，rebase 永远不会冲突。 

# 日常跟随上游，固定四步
git checkout main
git pull                       # 永远快进：main 无自有提交
git checkout local/contract
git rebase main                # 永不冲突：文件集不相交

若连版本历史都不需要，还有更彻底的做法：把这些路径写进 .git/info/exclude （本地生效、不进版本库），文件就完全不存在于 Git 视野里，main 保持字节级纯净。 代价是换机器要重建，且无法共享。本仓 .git/info/exclude 已存在且为空，可直接用。

规则 4

只依赖 HTTP/WS 契约，绝不 import 上游内部路径

守卫层与客户端都只能通过 /api/* 和 /api/ws 与上游交互。 任何 from hermes_cli.xxx import yyy 形式的依赖都是违规的—— 那会把一条 Git 层面守得住的边界，泄漏成一条守不住的代码依赖。

上游 COMPAT_MANIFEST.md 首句：“Internal import paths are not a stable API.” 2026 年 9 月的一次拆分搬动了 1,148 个名字，兼容层只保留两天。这条规则不是洁癖，是上游明确的声明。

已知的一处偏差，需要你决定 本文档与集成方案文档目前放在 docs/ 下，而按规则 2，那是上游维护的目录。 风险很低（文件名足够独特，且不会被修改），但如果你希望严格执行规则 2， 应该把它们移到 contract/ 或另一个上游未占用的顶层目录下。

四、采纳的两个方案

各自的取舍
方案 1

黑盒进程 + 仓库外自建前端

能力层

不改一行上游 Python。hermes serve --port 9119 起后端；桌面端与 Web 端是独立项目， 只经 HTTP + WebSocket 调用。这也是上游为 serve 子命令写明的目标用法—— 它的官方描述原文就是「the JSON-RPC/WebSocket gateway the desktop app and remote clients connect to」。

升级代价
零。你对上游仓库的改动量是 0，git pull 永远快进。
后端能力
自动跟进。上游新增的模型、平台适配、工具，你 pull 完就有，不需要搬运任何代码。
初期工作量
前端全量自研。但传输层可直接复用 apps/shared/src/ 下的 948 行 JSON-RPC 客户端（MIT），不必重写协议。
唯一风险
接口漂移。近 180 天上游删了 311 条路由行，无 API 版本号、无弃用窗口。这正是方案 3B 存在的理由。
依赖面控制
官方桌面端消费 218 个端点，但对话型客户端只需约 57 个。用得越少，漂移能伤到的地方越少。
方案 3B

仓库内只加不改的契约守卫

保障层

在 hermes-agent 内新增一个目录，存放契约基线与漂移测试。它把方案 1 唯一的风险 从「上线后用户点不动按钮」提前到「同步上游时 CI 变红」。

升级代价
零。只新增文件，Git 对新增文件不产生冲突；提交在独立分支上，main 保持纯净。
守什么 · REST
web_server.py:296 没有禁用 openapi_url，/openapi.json 可达（需带令牌）。抓下来存基线，同步后 diff。
守什么 · WS
OpenAPI 覆盖不到对话主干。279 个 RPC 方法名与 23 个事件名不在 /openapi.json 里——FastAPI 只知道有个 /api/ws。必须单独建快照，这是自动化最薄弱的一环。
告警范围
只对你实际使用的端点与方法报警。上游一年新增 549 条路由行，全量 diff 会每周都红，噪音会让告警失效。
放弃成本
删掉目录即可，不留任何残骸——因为它从未修改过上游的任何一个字节。

五、弃用留档

为什么排除，以及何时该重新考虑

记下排除理由，是为了将来前提变化时能快速判断要不要翻案，而不是重新论证一遍。

方案 2 · 抽成独立 Python 包 / 仓库

排除理由：与「跟随主线」直接冲突。web_server.py 一年 715 次提交，每次都要人工 port； 它对 hermes_cli 有 262 处 import，且依赖的是配置、鉴权、工具配置这些核心层，抽 B 线等于抽走整个 hermes_cli（479 模块 / 20.9 万行）；/api/ws 还直接 import tui_gateway.ws， 那个包一年 1,305 次提交。付出全部代价后，产出物与方案 1 直接跑 hermes serve 完全等价。

何时翻案：当「跟随上游」不再是目标时——例如要把后端作为产品交付第三方、自己承诺 API 版本与 SLA。 那是一次不可逆分叉，之后上游的新模型与新能力都与你无关。

方案 3A · 重构既有文件建立边界

排除理由：要重构的正是全仓变更最快的文件——web_server.py(715/年) + web_routers/(183/年)，约每天 2.5 次上游提交落在你改过的区域。 每次 git pull 都是一次手工三方合并，而且合并的是你不熟悉的上游改动。 它会立刻终结当前「零自有提交」的干净状态。

何时翻案：当你打算把这层边界以 PR 形式提给上游时。一旦合并，冲突问题自动消失—— 因为你的代码就是上游代码。架构图第 4 页指出的「gateway 被当作核心服务，实际却在向外索取依赖（I=0.62）， cron、tui_gateway、web_server、acp 都直接 import 它的子模块而非通过稳定接口」， 说明这个方向技术上站得住。但成败取决于上游是否接受，不由你控制。

六、验收：怎么证明「零冲突」是真的

可执行的检查

这个架构的核心承诺是可验证的，不需要靠感觉。下面三条随时可以跑，任何一条不成立就说明规则被破坏了。 

# 检查 1：main 是否仍是上游纯镜像（期望输出 0　0）
git rev-list --left-right --count origin/main...main

# 检查 2：自有分支是否只新增、未修改上游文件（期望只有 A 开头的行）
git diff --name-status main...local/contract

# 检查 3：守卫层是否误 import 了上游内部路径（期望无输出）
grep -rn "from hermes_cli\|import hermes_cli\|from tui_gateway" contract/
把检查 1 和 2 放进同步脚本 跟随上游的那四条命令外面套一层这两个检查，规则就从「文档里的约定」变成「跑不过就停下」。 规则 4 的检查 3 则应该进 CI，和契约漂移告警放在一起。
