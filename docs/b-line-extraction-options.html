Hermes-Agent · 架构决策备忘

B 线能不能单独抽出来

把端到端架构图里「B · hermes serve 桌面 / Dashboard 后端」这条线剥离出来、自建桌面端与 Web 端， 同时继续跟随上游 NousResearch/hermes-agent 升级——三种做法的成本、风险与真实产出对比。

仓库 qlshouyu/hermes-agent（fork） 分支 docs/hermes-process-map 基线 fc71fb63e5 · v0.21.2 日期 2026-09-12

先给结论

能抽，但抽的不是代码，是契约。 B 线在代码层面无法剥离——它对 hermes_cli 有 262 处 import，依赖的又恰好是配置、鉴权、工具配置、插件这些核心层， 抽 B 线等于抽走整个 hermes_cli（479 模块、20.9 万行）。 但 B 线在进程和协议层面早已是独立的：hermes serve 启动时会设 HERMES_SERVE_HEADLESS=1 关掉内置前端， 只暴露 241 个 REST 端点 + 一条 JSON-RPC WebSocket——这个模式就是为外部前端准备的。

因此推荐方案 1：把 hermes serve 当黑盒后端进程，前端在仓库外自建。 它是三个方案里唯一能做到「升级永远零冲突」的，因为你对上游仓库的改动量是零。 代价是把风险从「合并冲突」换成了「接口漂移」——而漂移是可以用契约快照测出来的，冲突不能。

三、上游已经给外部前端开好的口子

方案 1 的可行性前提

在读代码之前我以为方案 1 需要打补丁。实测下来不需要——这四个口子是现成的，说明「只跑后端、前端你自己来」是被支持的用法。

无头模式关掉内置前端
hermes serve 会在导入 web_server 之前设 HERMES_SERVE_HEADLESS=1， mount_spa() 随之不挂载。后端只剩 API，不会跟你的前端抢路由。 hermes_cli/main_dashboard.py:713 · _resolve_dashboard_web_dist()
CORS 放行任意本地端口
allow_origin_regex = ^https?://(localhost|127\.0\.0\.1)(:\d+)?$—— Vite dev server 跑在 5173、打包后跑在别的端口，都不用改后端。 hermes_cli/web_server.py:381
WebSocket 信任非 Web 源
Origin 是 file:// / app:// / null 时直接放行（打包后的 Electron 就是这种）； 是 http(s) 时只比对主机名、忽略端口。自建桌面端与本地 Web 端都能直连 /api/ws。 web_server_chat.py:165 · web_server.py:537 _is_accepted_host()
Token 可由你固定
HERMES_DASHBOARD_SESSION_TOKEN 环境变量会被直接采纳为会话令牌（否则每次启动随机生成）。 另有 --ssh-session-token-file，且该参数只对 serve 开放——又一处「serve 是给外部调用方用的」的证据。 web_server.py:308 · main.py:2427

四、三个方案逐一剖析

成本 · 升级代价 · 真实产出
方案 1

黑盒进程 + 仓库外自建前端

推荐

一行 Python 都不改。hermes serve --port N 起后端；你的桌面端和 Web 端是 hermes-agent 之外的独立项目， 只通过 HTTP + WebSocket 调用。上游仓库对你而言是只读的。

升级代价
零。git pull 永远不会冲突，因为你对上游文件的改动量是 0。这是三个方案里唯一做到这点的。
初期工作量
前端全量自研。但传输层可直接复用 apps/shared/src/ 下的 JSON-RPC 客户端，不必从零实现 279 个方法的协议。
真实风险
接口漂移。180 天删了 311 条路由行，上游随时可能改掉你依赖的端点，而且不会通知你。这个风险不会因为选别的方案而消失——方案 2、3 只是把它伪装成了合并冲突。
缓解手段
漂移可测：抓 /openapi.json 存基线快照，每次 pull 后 diff，只对你实际用到的端点子集报警。冲突不可测，只能人工解。
作用域
你大概率只需要 218 个端点里的 30–50 个（会话、消息、配置、模型）。依赖面越小，漂移暴露越小。
放弃成本
低。前端是独立项目，随时可以换后端或退回官方 Dashboard，不留残骸。
方案 2

抽成独立 Python 包 / 仓库

不建议

把 web_server.py + web_routers/ 物理搬到新仓库或新包，独立发版，反转 262 处 hermes_cli 依赖。

依赖真相
被依赖最多的是 web_deps(21)、config(19)、web_models(18)、auth(13)、tools_config(10)、plugins_cmd(10)。 这些是 Hermes 的配置与身份核心，不是外围工具。抽 B 线 = 把 hermes_cli（479 模块 / 20.9 万行）一起抽走。
对话主干拦路
/api/ws 里直接 from tui_gateway.ws import handle_ws。要么把 tui_gateway（一年 1,305 次提交）一并抽走，要么放弃对话功能——而对话正是你要做的产品核心。
升级代价
web_server.py 一年 715 次提交，约每周 14 次。每一次都要人工 port 到你的独立包。这不是一次性迁移，是一份常设岗位。
结构性风险
上游白纸黑字声明内部导入路径不稳定，且刚演示过一次搬动 1,148 个名字。你的抽取层建立在明确不被承诺的地基上。
产出物
付出全部这些代价之后，你得到的是——一个 HTTP + WebSocket 后端。和方案 1 直接跑 hermes serve 拿到的东西，功能上完全一致。
核心判断 方案 2 的成本最高，而产出与方案 1 等价。唯一的额外收益是「代码归我管」——但只要你还想跟随上游升级，这份所有权就是净负债。
方案 3

留在仓库内，重构出清晰边界

分两种，结论相反

仍在 hermes-agent 里，把 B 线收拢成有明确接口的子系统。这个方案必须拆成两个变体来判断，因为它们的升级代价差了几个数量级。

变体 A
改既有文件
不建议。你要重构的正是全仓变更最快的文件：web_server.py(715/年) + web_routers/(183/年) ≈ 每天 2.5 次上游提交落在你改过的区域。每次 git pull 都是一次手工三方合并，且合并的是你不熟悉的上游改动。 当前 fork 的自有提交数是 0（git log 作者全是上游贡献者），这份「零冲突债务」会在动第一刀时结束。
变体 B
只加不改
可取，且建议与方案 1 组合。只在仓库内新增文件——比如一个 contract/ 目录，放 OpenAPI 基线快照、 契约测试、以及（可选）一个薄的聚合 router，不碰任何既有文件。 Git 对新增文件永不产生冲突，所以升级代价仍然是零。
变体 B 的价值
它把方案 1 唯一的风险（接口漂移）变成 CI 里一条会失败的测试。你在合并上游代码的那一刻就知道哪个端点变了，而不是在用户点不动按钮的时候。

六、什么情况下该推翻这个推荐

方案 2 / 3A 的合理适用场景

上面的判断建立在「你要持续跟随上游升级」这个前提上。前提变了，结论就变。

选方案 2，如果——你打算不再跟随上游

比如要把这个后端作为产品交付给第三方，需要自己承诺 API 版本与 SLA。 那么「不能跟随升级」就不再是成本而是设计目标，方案 2 的全部代价立刻变得合理。 但这是一次不可逆的分叉：分叉之后上游的新模型、新平台适配、新工具都与你无关。

选方案 3A，如果——你打算把改动回推上游

如果这层边界是以 PR 形式提给 NousResearch/hermes-agent 的， 合并冲突这个问题会自动消失——因为合并之后，你的代码就是上游代码。 考虑到架构图第 4 页已经指出「gateway 被当作核心服务、实际却在向外索取依赖，cron、tui_gateway、 web_server、acp 都直接 import 它的子模块而不是通过稳定接口」， 这个方向在技术上是站得住的。但它的成功取决于上游是否接受，不完全由你控制。

七、若选方案 1，第一步做什么

全部可在现有 HEAD 上验证
  1. 用固定 token 起一个无头后端 确认它只暴露 API、不挂载前端，并用这个 token 打一个已知端点验证鉴权。 
    HERMES_DASHBOARD_SESSION_TOKEN=dev-fixed-token \
  hermes serve --port 8765
  2. 抓取并冻结契约基线 FastAPI 自带 /openapi.json，把它作为你和上游之间的合同原件存进版本库。
  3. 圈定你真正需要的端点子集 桌面端 218、Web 端 130 只是上限。先列出你的产品实际要的那 30–50 个，依赖面越小漂移暴露越小。
  4. 打通 /api/ws 的 JSON-RPC 客户端 这是对话主干，也是唯一非 REST 的部分。直接移植 apps/shared/src/json-rpc-gateway.ts 与 websocket-url.ts，不要重写协议。
  5. 加一条漂移告警 每次同步上游后重新抓 openapi，与基线 diff，只对子集内的变化失败。这一步就是方案 3B——仓库内只加不改的那个目录。
