启动命令与参数

6 条入口

web_server.py 自己不是可执行入口，它由 hermes dashboard 与 hermes serve 两个子命令共用的 cmd_dashboard / start_server() 拉起。二者共享同一个 FastAPI app，差别只在 headless_backend 这一个开关上。

常用启动方式

# 1. 本机 Web UI（构建并挂载 SPA，自动开浏览器）
hermes dashboard

# 2. 指定端口与地址；容器里常用这一组
hermes dashboard --host 0.0.0.0 --port 9119 --no-open

# 3. headless 后端：只有 JSON-RPC / WS / API，不构建也不挂载 SPA
hermes serve --host 127.0.0.1 --port 0

# 4. 指定 profile（-p/--profile 是顶层参数，必须写在子命令之前）
hermes --profile work dashboard

# 5. Electron 桌面端实际派生的命令
python -m hermes_cli.main serve --profile <name> --host 127.0.0.1 --port 0

# 6. 查看 / 停止正在监听的实例
hermes dashboard --status
hermes dashboard --stop
不要直接用 uvicorn 起

hermes_cli/web_server.py:296 的 app 虽然是模块级 FastAPI 对象，技术上能被 uvicorn hermes_cli.web_server:app 加载，但这样会跳过 start_server() 里的鉴权门禁初始化（_configure_auth_gate，web_server.py:1405）、端口冲突探测与 ready 文件写入。官方没有文档化这条路径。另外文件头注释里写的 python -m hermes_cli.main web 是过期文档——argparse 树里根本没有 web 子命令。

端口回报机制

--port 0 时父进程需要知道内核实际分配了哪个端口。后端同时用三条通道回报（web_server.py:1247-1276）：

通道触发条件内容
ready 文件设了 HERMES_DESKTOP_READY_FILE原子写入 {"port": N}。Windows pythonw.exe 无控制台时靠它轮询。
fd 1 哨兵行始终写真实 fd 1 而非 sys.stdout（tui_gateway.server 会把 stdout 重定向到 stderr）。内容是 HERMES_BACKEND_READY port=N 或 HERMES_DASHBOARD_READY port=N。
人类可读行始终URL 或监听地址。

端口被占用时走 _report_port_in_use：写 BACKEND_PORT_IN_USE port=N 哨兵，然后 sys.exit(75)（BSD EX_TEMPFAIL），而不是让 uvicorn 抛裸 ERROR。实际端口从 uvicorn 已绑定的 socket 读取，避免「先探测再绑定」的 TOCTOU 竞态。

鉴权

后端有两套并存的鉴权模式，由绑定地址与是否配了 provider 决定走哪一套。REST 与 WebSocket 的做法不同，这是最容易踩坑的地方。

模式一：loopback token（默认）

进程启动即确定 _SESSION_TOKEN：优先取 HERMES_DASHBOARD_SESSION_TOKEN，否则 secrets.token_urlsafe(32) 随机生成（web_server.py:307）。进程存活期内固定，退出即失效。

通道凭据传递方式
REST请求头 X-Hermes-Session-Token，或旧式 Authorization: Bearer <token>。常数时间比较。
下载类端点额外允许 ?token= 查询参数（如 /api/files/download）。
WebSocket只能用 ?token= 查询参数——浏览器无法为 WS 握手设置 Authorization 头。
SPA不用手动填：_serve_index 把 window.__HERMES_SESSION_TOKEN__ 内联进 index.html。

token 不会打印到终端，终端只打印 URL。浏览器加载页面时自动拿到它。

模式二：gated（OAuth cookie / basic auth）

绑定非回环地址，或设了 dashboard.public_url，就切到这一套。此时 loopback 的 _SESSION_TOKEN 校验被整体跳过，避免两套逻辑打架。

通道凭据传递方式
RESTcookie session，或 RFC 8252 native bearer token。未通过时 API 路径返回 401 JSON，HTML 路径 302 跳 /login。
WebSocket短时 ?ticket=（30 秒 TTL、一次性，由 POST /api/auth/ws-ticket 铸造），或 ?internal=（进程生命周期内可重用，只发给服务端自己派生的 WS 客户端，从不下发给 SPA）。
WebSocket 的 ?token=被拒绝。防止泄露的 _SESSION_TOKEN 在 gated 模式下越权访问网关。
fail-closed

只要 --host 不在 {localhost, 127.0.0.1, ::1} 里就判定为公开（RFC1918 内网、CGNAT、link-local 一律算公开——局域网设备在威胁模型里是不可信的）。此时若一个鉴权 provider 都没配好，start_server 直接 SystemExit 拒绝启动，并在报错里说明触发原因与修复办法（配 dashboard.basic_auth.* 或跑 hermes dashboard register）。非 headless 且有 TTY 时，会先弹一个交互式向导让你当场选。

免鉴权白名单

下列路径两套鉴权门都放行（hermes_cli/dashboard_auth/public_paths.py）。这份清单被两个中间件共用，就是为了防止两边漂移——曾经漂移过一次，导致 /api/status 被 401，打断了 portal 的无 cookie 存活探针。

/api/health /api/status /api/config/defaults /api/config/schema /api/model/info /api/dashboard/themes /api/dashboard/plugins /api/cron/fire

/api/cron/fire 是特例：它不走 cookie 门，但自带 NAS 签发的短时 JWT（purpose=cron_fire）并由处理函数校验——安全边界是那个 JWT，不是这份白名单。

WebSocket 的额外校验

WS upgrade 不经过 HTTP 中间件，所以 Host / Origin 的 DNS-rebinding 防护要在 WS 路由里单独实现（web_server_chat.py:137-199）。回环模式下还会校验对端 IP；非回环或 gated 模式放行任意对端，因为门槛已经在别处了。
