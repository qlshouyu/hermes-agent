零、先确认一件事：这是上游的预期用法

不是变通

在设计任何东西之前，先把这个前提钉死——否则整个方案建立在「钻空子」的心理负担上。 上游为 serve 单独建了一个子命令解析器，它的官方描述是这样写的：

Run the Hermes backend server — the JSON-RPC/WebSocket gateway the desktop app and remote clients connect to. Headless: it never opens a browser UI.

hermes_cli/subcommands/dashboard.py:68 · build_serve_parser() 的 description

serve also skips the web UI build (headless_backend=True): pure JSON-RPC/WS clients never load the SPA.

hermes_cli/subcommands/dashboard.py:5 · 模块 docstring

serve: same gateway as dashboard, never opens a browser. Exists so the desktop app / remote backends launch a backend WITHOUT invoking dashboard — independent surfaces that merely share this server.

hermes_cli/subcommands/dashboard.py:92 · 子命令注册处的注释

结论 「纯 JSON-RPC/WS 客户端」不是我们发明的用法，是上游写在代码注释里的目标用户。 官方桌面端 apps/desktop 自己就是这么接的——它和你要做的客户端，在后端眼里没有区别。

启动、就绪判定、关停

# 起一个可被外部客户端连接的后端（token 由你固定，便于开发）
HERMES_DASHBOARD_SESSION_TOKEN=$MY_TOKEN hermes serve --host 127.0.0.1 --port 9119

# 就绪探针：/api/health 在公开白名单里，不需要 token
curl -sf http://127.0.0.1:9119/api/health

# 带凭据读状态（版本、网关状态、会话数、认证形态）
curl -s http://127.0.0.1:9119/api/status \
  -H "X-Hermes-Session-Token: $MY_TOKEN"

# 关停
hermes serve --stop
令牌来源
HERMES_DASHBOARD_SESSION_TOKEN 存在则直接采用；否则每次启动生成随机 32 字节 urlsafe 串，随进程消亡。 开发期固定它，生产期让它随机并由启动方捕获。 web_server.py:308 · _resolve_session_token()
无头判定
serve 在导入 web_server 之前 设 HERMES_SERVE_HEADLESS=1，mount_spa() 因此不挂载。 非 /api/* 的路径不会被上游 SPA 占用，你的前端可以自由使用根路径。 main_dashboard.py:713 · _resolve_dashboard_web_dist()
空闲退出
只在传了 --ssh-session-token-file 时启用。 机制是统计已接受的 WebSocket 连接数，连续 900s 为零且无进行中的 Agent 轮次才优雅退出（轮次探测不确定时按「不退出」处理）。 普通本地启动不会自动退出——你的客户端不必为此发心跳。 web_server_idle_exit.py:1 · DEFAULT_IDLE_GRACE_S = 900.0
配置容错策略
serve 是非交互的，遇到损坏的 config.yaml 会直接退出码 2，而不是静默用默认值启动 （避免供应商自动探测误用无名 .env 凭据）。你的启动器要能区分「配置错误」和「端口占用」。 main.py:2405 · _dashboard_validate_serve_args()

五、WebSocket 契约：对话主干

/api/ws · 唯一的非 REST 部分

这是整个集成里最需要认真对待的一段。它不是 REST，也不是自定义协议—— 它是和 Ink 终端前端走 stdio 时一模一样的那套 JSON-RPC，只是换了传输层。

WebSocket transport for the tui_gateway JSON-RPC server: reuses dispatch verbatim so every RPC, slash command, approval flow and agent event takes the same handlers as Ink over stdio. Wire protocol is identical to stdio (newline-delimited JSON-RPC both ways; gateway.ready right after accept).

tui_gateway/ws.py:1 · 模块 docstring

帧格式
换行分隔的 JSON-RPC，双向对称。与 hermes --tui 走 stdio 时的字节流一致，这意味着协议有两个独立实现方在持续验证它。
握手
服务端 accept 之后立即推送 gateway.ready。客户端应当以收到它作为「连接可用」的判据，而不是 WebSocket 的 open 事件。
心跳
客户端每 15s ping 一次；服务端单帧发送截止 30s；客户端心跳死线 45s。 超过 30s 排不出约 48 KiB 的对端会被主动关闭以触发重连，而不是让后续所有帧堵在写锁后面。 tui_gateway/ws.py:67 · _WS_SEND_DEADLINE_S
流式合并
message.delta / reasoning.delta / thinking.delta 三类逐字事件被缓冲， 按 33ms（约 30fps）批量刷出，避免每个 token 都唤醒事件循环去和 Agent 轮次抢 GIL。 其他事件（工具、审批、状态、完成）不合并，且会先把缓冲区刷掉再发自己——顺序有保证。 tui_gateway/ws.py:75 · _STREAMING_EVENT_TYPES
长任务
属于 _LONG_HANDLERS 的方法被派到线程池，dispatch 立即返回 None， 由 worker 自己通过绑定的 transport 回写响应。客户端必须按 id 异步配对，不能假设请求-响应同步。 tui_gateway/server.py:780 · dispatch()
规模

七、契约漂移防护

方案 3B · 仓库内只加不改

方案 1 的唯一真实风险是接口漂移——近 180 天上游删了 311 条路由行， 而且没有 API 版本号、没有弃用窗口。好消息是这个风险可以被测出来。

REST 面可快照
web_server.py:296 创建 FastAPI app 时没有禁用 openapi_url， 所以 /openapi.json 是可达的（需带令牌，它不在公开白名单里）。 抓下来存为基线，每次同步上游后重抓并 diff。
WS 面不在 OpenAPI 里
这是最容易被漏掉的一点。279 个 JSON-RPC 方法名和 23 个事件名不会出现在 /openapi.json 中—— FastAPI 只知道有一个 /api/ws 端点。对话主干恰恰是你最依赖的部分，却是自动化覆盖不到的部分。 必须为它单独建快照：从 tui_gateway/methods_*.py 提方法名、从 apps/shared/src/json-rpc-gateway.ts 的 GatewayEventName 提事件名。
只对子集报警
全量 diff 会每周都红——上游一年新增 549 条路由行，绝大多数与你无关。 把告警范围限定在你 MVP 清单里的那 57 个端点 + 你实际调用的那些 RPC 方法上， 否则告警会因为噪音而被忽略，等于没有。
放在哪
在 hermes-agent 仓库内新建一个上游未占用的顶层目录——已实测确认 contract、contracts、integration、client、 sdk 在 origin/main 中全部空闲。 只新增文件，不碰任何既有文件；Git 对新增文件不产生冲突，升级代价因此仍是零。 不要放进 docs/ —— 那是上游维护的目录，23 个文件、239 次提交/年
提交到哪
提交到一条自己的分支（如 local/contract），绝不提交到 main。 main 与 origin/main 不分叉，git pull 才能永远是快进； 自有分支因为与上游文件集不相交，git rebase main 永远不会冲突。 当前实测：main 与 origin/main 落后 0 / 领先 0，零冲突债务

跟随上游的固定四步

git checkout main
git pull                       # 永远快进：main 无自有提交
git checkout local/contract
git rebase main                # 永不冲突：文件集不相交
这条边界的完整规则 四条规则（main 只读 · 专用顶层目录 · 独立分支 rebase · 只依赖 HTTP/WS 契约） 与它们的验收检查，记录在配套文档《hermes serve 抽取方案对比》第三、六节。 其中规则 4 尤其关键：守卫层与客户端都不得 import 任何 hermes_cli.* / tui_gateway.* 路径， 否则一条 Git 层面守得住的边界会泄漏成一条守不住的代码依赖。
