进程拓扑 — 谁派生了谁

按部署形态分三支

Hermes 没有单一的进程树，而是三条并行的派生链，共用同一组“工具子进程扇出”。最容易画错的一条边是 Desktop：hermes serve 是 Electron 的子进程、随 App 退出；而消息网关是分离派生（detached）的，故意脱离 App 生命周期，这样 App 关掉后机器人还在跑。

容易画错的三条边

① cron 不是进程。 默认由 InProcessCronScheduler 跑在 gateway 进程的 cron-scheduler 线程里；cron/scheduler_detached_worker.py 里的 “detached worker” 指的是 ThreadPoolExecutor 线程，不是 OS 进程。

② 子智能体委派不是进程。 delegate_tool / kanban swarm 的子 Agent 是同进程内的对象，配合 asyncio 与线程运行。

③ Dashboard 不派生 TUI 后端。 web_server.py 直接 import tui_gateway.server，在自己进程里跑轮次；浏览器与 Electron 渲染进程是通过 WebSocket 接进来的，不是管道。

模块分层依赖脊柱

AST 扫描 1,635 个模块，仅计模块级 import

下图只画模块顶层的 import（即 import 时刻真正成立的依赖）。函数体内的延迟导入被刻意排除——那是这个代码库用来打破环的手段，混进来会让整张图变成一团糊。

分层不是无环的 — 环被延迟导入吃掉了

agent/ ⇄ hermes_cli/ 在模块级是 28 ⇄ 28，看上去只是小幅互引；但函数体内的延迟导入是 355 ⇄ 351。tools/ ⇄ hermes_cli/、gateway/ ⇄ hermes_cli/ 同理。这正是 AGENTS.md 里 “facade + siblings” 约定的直接后果：兄弟模块在函数里 from <facade> import name，既打破了 import 环，也决定了测试打桩要打在门面上而不是定义处。读这张图时要记住：静态的层次感是靠约定维持的，不是靠物理隔离。

03

工具运行时链 — 顺带纠一处文档偏差

图 2 中“工具运行时”一层的展开

工具层是全项目唯一一处“导入即产生副作用”的设计：model_tools.py 在模块顶层调用 discover_builtin_tools()，发现式地 import 全部 299 个工具模块，每个模块在导入时向 registry 自注册。谁 import 了 model_tools，谁就一次性付掉整套工具发现的成本。

文档与代码不一致

AGENTS.md:220 写的依赖链是 tools/registry.py ← tools/*.py ← model_tools.py ← run_agent.py, cli.py, batch_runner.py, environments/。前三段完全属实，但末尾把 environments/ 列为 model_tools.py 的下游消费者方向反了：grep -rn "model_tools" tools/environments/ 结果为空，而 tools/terminal_tool_backends.py 等反过来 import tools.environments.*。真实位置是链条的最上游。修正后应写作 tools/environments/ ← tools/*.py。

05

五个值得记住的结论

一个内核，七个宿主

run_agent.AIAgent 是全项目唯一的收敛点

CLI、gateway、tui_gateway、cron、acp_adapter、batch_runner 六路都 from run_agent import AIAgent，dashboard 经 tui_gateway 间接构造。要改动轮次行为，这里是唯一的必经之路——也是为什么 AGENTS.md 把“核心是窄腰”写成第一条不变量。

唯一旁路

mcp_serve.py 不是一个 Agent 进程

它既不构造 AIAgent 也不加载 tools registry，只通过 hermes_state_registry 读取其它进程落盘的 state.db，把会话与消息暴露成 MCP 工具。把它画进 Agent 主链是错的：它是一个只读旁路桥。

最易画错的一条边

Dashboard → tui_gateway → run_agent

web_server.py 从不直接 import run_agent，而是把整个 tui_gateway.server 拉进自己进程跑轮次（web_server.py:174）。它同时还大量依赖 gateway.* 的状态与控制模块，是全项目耦合面最广的入口。

依赖方向反直觉

plugins 依赖 gateway，而不是被 gateway 依赖

22 个平台适配器住在 plugins/platforms/，继承 gateway.platforms.base，形成 120 处模块级 plugins → gateway。核心不认识插件，插件认识核心——这正是“能力在边缘”的物理体现。

游离于统一基建之外

两个入口不走 hermes_logging

mcp_serve.py 用 logging.basicConfig，acp_adapter/entry.py 自建 RedactingFormatter 输出到 stderr（stdout 必须留给协议）。后者有充分理由，前者更像是历史遗留——这两个进程的日志不会出现在 hermes logs 里。

进程边界的设计意图

网关脱离桌面 App 是刻意的

hermes serve 随 App 退出，gateway run 用 start_new_session / DETACHED_PROCESS 分离派生，让 before-quit 的 SIGTERM 触达不到它，关掉桌面后机器人继续在线。gateway/AGENTS.md 明确写了“不要把网关重新挂回后端之下”。

分析方法：对 1,635 个 Python 模块做 AST 全量扫描统计 import（排除 tests/ evals/ website/），叠加对 Popen·spawn·fork·execv·multiprocessing 的全仓追踪与 s6 / docker-compose 服务定义核对。行数与文件数为扫描当时口径。
